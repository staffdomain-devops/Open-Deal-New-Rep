# Lane A Owner-Changed Re-Engagement Pipeline

## What This Is

A per-contact generation pipeline that produces 8 personalised deliverables for a past prospect where the HubSpot contact owner has changed. A HubSpot workflow fires when a contact with an open deal gets a new owner and sends just that contact ID (via `repository_dispatch`). Deterministic code fetches everything HubSpot knows about the contact (company, all company contacts, all company deals, notes, engagements), **Agent 1 (Research)** analyzes that raw data against the build spec's rules and produces a verdict (proceed/hold/exclude) plus an assembled research brief, and **Agent 2 (Build)** generates 5 re-engagement emails + 2 call-task briefings + 1 pinned contact note from that brief. All output is written back to HubSpot for that one contact.

## Core Value

Every new account owner inherits a warm relationship they have never personally touched. The pipeline turns the file into a credible, personalised handover sequence — so the rep sounds like they've read the notes, because the generation input includes the notes.

### Out of Scope

- Breeze prompt generation — this pipeline writes finished emails

## Context

Architecture mirrors the Inbound pipeline (`C:\Users\irahfo\Outreach\Inbound\`) in structure (Python scripts, GitHub Actions, `utils.py`, `requirements.txt`, `RUNNER_TEMP` JSON hand-off). Key differences from Inbound:

| Dimension | Inbound | Lane A |
|---|---|---|
| Trigger | Per-contact via Make.com | Per-contact via HubSpot workflow → `repository_dispatch` |
| Data assembly | Simple fetch + enrich | Deterministic fetch (company, contacts, deals, notes, engagements) handed to Agent 1, which applies exclusion, colleague selection, notes/sensitivity triage, and brief assembly |
| Deliverables | 1 email | 8 (5 emails + 2 call notes + 1 pin), generated by a second agent (Agent 2) from Agent 1's brief |
| HubSpot write | 2 properties + 1 note | 12 properties (`email_1_subject`…`email_5_body` + `task_note_1` + `task_note_2`) + 1 pinned note |
| Lint | Basic (em-dash, JSON) | 18 checks (12 hard v1.0 + 6 hard v1.1) |
| Model | `claude-sonnet-4-6` | `claude-sonnet-5` |
| System prompt | Short inline | Long verbatim (cached, `cache_control: ephemeral`) — one for each agent |
| Max tokens | 2048 | 2000 (Agent 1) / 3000 (Agent 2) |
| Batch API | No | No — one contact per run, realtime call only |
| Routing | None | 14-row vertical table → case study + URLs (deterministic) |
| Close bank | None | 5 options; 3 rule-based, 2 random fallback (deterministic) |

Reuse `utils.py` from Inbound unchanged — same retry/DLQ patterns apply.

## Key Decisions

| Decision | Rationale | Outcome |
|---|---|---|
| Per-contact trigger via `repository_dispatch`, not batch/list | Batch runs didn't hold up at volume (single long serial job, single failure domain, needed a pilot-cap workaround); a HubSpot workflow now sends one contact ID per open-deal owner change | Confirmed 2026-09-01 |
| Two-agent split: Agent 1 (Research) then Agent 2 (Build) | Judgment calls (colleague selection, notes/sensitivity triage, exclusion verdicts) move into an LLM reasoning step instead of regex/heuristics; Agent 2 stays a pure writer from Agent 1's brief, matching spec's "model never fetches/infers, only writes from the brief" rule | Confirmed 2026-09-01 |
| Reuse utils.py from Inbound | Same retry/DLQ/backoff patterns; no divergence needed | — Pending |
| One Claude call per contact, all 8 deliverables (within Agent 2) | Model needs full arc to avoid repetition; call notes reference email content | — Pending |
| Realtime API only, no Batch API | Batch API was a cost optimization for hundreds of contacts in one job; irrelevant once each webhook trigger handles exactly one contact | Confirmed 2026-09-01 |
| Cached system prompt (one per agent) | Long verbatim prompts; 10% price on cache hits across separate invocations | — Pending |
| HubSpot write-back uses `hs_object_id` match, single-object update | One contact per run; batch update API no longer needed | Confirmed 2026-09-01 |
| Call tasks created manually by rep; pipeline writes briefing to `task_note_1`/`task_note_2` | Simpler pipeline; rep controls task timing | Confirmed 2026-08-21 |
| Note pinning via engagements API | Verify support at pilot; manual fallback if API doesn't support pinning | — Pending |
| Close-bank fallback rotation (1↔2) replaced with random choice | The old rotation counter assumed one long-lived batch process; isolated per-contact runs have no shared state to rotate against | Confirmed 2026-09-01 |
| E1-E6 exclusion filtering left out of this repo entirely (not just out of Agent 1) | Later commits removed exclusion/verdict gating from Agent 1 without replacing it elsewhere; this repo currently trusts the upstream HubSpot workflow to only fire the webhook for eligible contacts | Flagged 2026-09-21 — needs JP confirmation that the HubSpot-side workflow actually enforces E1-E6, since it cannot be verified from this codebase |
| Contact-departure check (E7) added as mechanical Stage 1 logic, not an Agent 1 judgment call | v1.1 checklist item 17 was otherwise unimplemented; a regex/name-proximity check needs no LLM judgment and can run before any Anthropic API cost is spent | Confirmed 2026-09-21 |
